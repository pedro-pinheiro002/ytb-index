# Ingest becomes a budgeted, resumable rolling refresh of per-video CommentSamples

A Channel's comment volume, not its video count, sets the cost of an Ingest. The channel-wide `commentThreads.list?allThreadsRelatedToChannelId` stream (spec v1 §5 step 8) costs 1 unit per 100 threads, plus at least 1 `comments.list` unit for every thread with more than the 5 Replies YouTube embeds. A Channel with a million threads (Investidor Sardinha is in that range) needs more than 10,000 units, so it can never finish inside the 9,500-unit run budget. The run is also all-or-nothing (ADR-0001, `createBufferingSink`), so each retry hits the same wall and keeps nothing. We make two changes together. **First, comments are fetched per VideoRecord as a CommentSample**: one `commentThreads.list?videoId=…&order=relevance&maxResults=100` page holding the most relevant threads and only the Replies YouTube embeds, at 1 unit per VideoRecord whose `commentCount > 0`. **Second, an Ingest becomes a bounded pass over a per-video RefreshQueue** instead of one run over the whole Channel. Each pass spends at most a quota budget and a D1 row budget. It works through the VideoRecords that have never been sampled first, then the ones whose sample is closest to ADR-0001's 30-day expiry. It writes each VideoRecord's sample as soon as it is fetched and stops cleanly when either budget runs out. A daily scheduled pass per enrolled Channel keeps the whole Catalog inside the 30-day window on a rolling basis. ADR-0001's limit stops being something to beat in a single run and becomes the cycle length the refresh is planned around.

## Status

proposed. It contradicts and, if accepted, amends:

- **ADR-0001**: "re-run overwrites all `fetched_at` values for that channel in one transaction" and "partial refreshes are out of v1 scope" no longer hold. `fetched_at` becomes per VideoRecord and per CommentSample, and partial refreshes are the normal case. The 30-day rule and read-time redaction are unchanged.
- **ADR-0003**: the local all-or-nothing transaction shrinks to one VideoRecord's sample. The remote side keeps its idempotent upserts.
- **ADR-0005**: adds a schedule ("no cron" no longer holds), makes "one active IngestRequest per Channel" also cover scheduled passes, and replaces "no per-run comment cap" with an explicit row budget.
- **ADR-0008**: a scheduled pass has no OperatorKey, because none is stored. See Consequences.
- **Spec v1 §5 step 8 and spec v2**: the channel-wide stream and full Reply paging stop being the default.

Validate before accepting. On a Channel small enough to Ingest in full today, compare the TimeAnchors and "Key moments" from the full stream with those from the CommentSamples. Also confirm the D1 rows-written figures below against production D1 on real rows. The decision rests on two hypotheses that are not yet verified: that timestamped comments rank high under `order=relevance`, and the row cost below.

## Considered Options

- **Keep the channel-wide stream, add checkpointing**: save the stream's `pageToken` and resume it the next day. Rejected. It fixes "never finishes" but not "costs too much": every refresh still pays for every thread, and `pageToken` lifetime is undocumented, so a cursor saved for a day may fail to resume.
- **Full per-video paging, resumable**: page `commentThreads.list?videoId=…` to the end for each VideoRecord, with a per-video cursor. Kept as the optional deep tier below, not the default. It costs at least the stream's price plus 1 unit per VideoRecord.
- **Filter at the source with `searchTerms`** (ADR-0011 already uses it): would pay only for matching threads, if YouTube's tokenizer can match timestamp text at all. Not adopted because it is unverified, and it would drop every comment without a timestamp from the Catalog and from the SearchQuery. Worth a 3-unit experiment. If it works, it can become another sample kind on the same RefreshQueue.
- **Comments on demand** (fetch when a Visitor opens a VideoRecord): rejected. Visitors would spend quota, the first view would be empty, and the SearchQuery would only cover pages someone already opened.
- **Unofficial sources (innertube, scraping)** or **several Google projects pooled for quota**: rejected. Both break YouTube's terms, as ADR-0009 already found for the unofficial sources.
- **Relevance CommentSamples on a budgeted rolling RefreshQueue (chosen)**.

## Consequences

- **Cost model.** A first pass over a Channel with _N_ VideoRecords costs about `N/50` (`playlistItems.list`) + `N/50` (`videos.list`) + `N` (one CommentSample each). For a few thousand VideoRecords that fits in one day's quota. Later passes cost `N/50` to list uploads, plus `videos.list` and a CommentSample only for new or due VideoRecords. Replies beyond the 5 embedded ones are not fetched in the sample tier.
- **D1 is the binding limit, not quota.** `comments` carries five indexes plus its primary-key index, and D1 counts every index entry as a row written. Measured on a local workerd D1 with the current upserts (`scripts/measure-comment-samples.ts`, synthetic rows), one CommentRecord costs 7 rows written, both new and on refresh, because the upsert re-sets indexed columns that never change. A TimeAnchor costs 2 new and 1 on refresh. That is roughly 14k CommentRecords a day on the free plan's 100k rows written, far less than 9,500 units can fetch. That refresh cost is already fixed independently of this ADR: the comment upsert no longer re-sets its immutable indexed columns (`video_id`, `channel_id`, `parent_id`, `author_channel_id`, `published_at`), so a refresh costs 1 row written per CommentRecord. New rows still cost 7, so for first passes the limit stays at about 14k new CommentRecords a day. A sample can hold up to 100 threads + 500 embedded Replies. So each pass carries a row budget next to its quota budget, and the CommentSample size (`maxResults`, default 100) is configurable per Channel. For a Channel the size of Investidor Sardinha, the honest options are a smaller sample or the Workers Paid plan (50M rows written per month). The ADR does not choose between them. The Operator does, per deployment.
- **Deep tier (optional, per Channel).** Budget left after all due samples are done may page a VideoRecord's threads in full (`order=time`, with Replies) and track a per-video cursor. Deep CommentRecords that are not refreshed within 30 days simply redact under ADR-0001. That is the existing safety net, not a new failure mode.
- **Schema** (a new numbered migration; `0001`–`0003` stay untouched): a `refresh_queue` keyed by video id (channel id, tier, `comments_fetched_at`, deep-tier cursor, last error), a per-Channel enrolment (enabled, sample size, deep tier on or off), and a quota ledger per Pacific-time day for the repository key. The ledger means a second pass on the same day starts from what that day has already spent, not from zero.
- **Priority** (deterministic, so it can be tested through the `now` seam): VideoRecords never sampled come first, newest `publishedAt` first. Then VideoRecords whose `comments_fetched_at` is older than a refresh margin (default 25 days), oldest first. VideoRecords with `commentCount = 0` are marked refreshed at no cost. VideoRecord metadata follows the same queue, in `videos.list` batches of 50.
- **Pipeline shape.** The comments stage stops emitting one buffered batch. It emits one batch per VideoRecord into a flushing sink, the shape ADR-0009's live-chat stage already uses (`src/ingest/stages.ts`). `QuotaExceededError` and the row budget become a normal end of a pass ("budget spent, _k_ VideoRecords still due"), with exit code 0 and a status the IngestRequest shows. A real `403 quotaExceeded` from Google still exits 2.
- **Schedule and keys.** The Worker gets a Cron Trigger that fires the existing `repository_dispatch` once a day per enrolled Channel. It reuses ADR-0005's path, and unlike a scheduled workflow it is not disabled after 60 idle days. A scheduled pass has no OperatorKey (ADR-0008 stores none), so it runs on the `YOUTUBE_API_KEY` repository fallback. An Operator-triggered IngestRequest with an OperatorKey runs one pass on that key's quota, as today. This touches `wrangler.jsonc`, which AGENTS.md lists as a danger zone, so it ships as its own change.
- **Product.** The Catalog is a sample. Each VideoRecord's page and the Channel page say so ("most relevant comments, refreshed <date>"), and LiveSearch (ADR-0011) remains the way to reach comments outside the sample. The SearchQuery (ADR-0010) covers only what was sampled.
- **Vocabulary.** "CommentSample" and "RefreshQueue" are new terms, and "Ingest" changes from "the single run that pulls one Channel" to "a budgeted pass". `GLOSSARY.md` is updated (through `/domain-modeling`) when this ADR is accepted, not before.
- **Free win, independent of this ADR.** Running `detectAnchors` over `description` (already fetched by `videos.list`) would add creator chapters at zero quota cost. `time_anchors` is keyed by comment today, so this needs its own record and is left to a separate change.

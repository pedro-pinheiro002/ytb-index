# ytb-index v2: Specification

> **Status:** draft, decisions settled (Phase A). Tickets follow in the wayfinder map.
> **Builds on:** [`v1.md`](v1.md). Anything v2 does not mention behaves as in v1.
> **Decisions:** [ADR-0007](../adr/0007-operator-supplies-own-api-key.md) (OperatorKey), [ADR-0008](../adr/0008-sealed-operator-key-to-actions-runner.md) (sealed key on Actions), [ADR-0009](../adr/0009-live-chat-official-api-active-broadcasts-only.md) (live chat), [ADR-0010](../adr/0010-catalog-search-normalized-like-not-fts5.md) (search), plus amendments to 0001/0002/0003/0005.
> **Vocabulary:** [`GLOSSARY.md`](../../GLOSSARY.md). New in v2: Broadcast, Reply, LiveChatMessage, OperatorKey, SearchQuery, SearchHit.

## Problem Statement

The Operator can build a Catalog of a Channel and browse it video by video, but cannot _find_ anything in it. There is no way to ask "who said X", "what was said in March", or "everything this author wrote". The Ingest runs on a key the Operator cannot change from the web app. Broadcasts look like plain uploads. Replies are dropped, so an author's activity is only half captured. The live chat of a Broadcast, often where the timestamped reactions are, is not captured at all.

## Solution

- The Operator pastes their own YouTube Data API key (the OperatorKey) into the web app. It is checked immediately with a clear verdict (valid, invalid, out of quota, API not enabled, restricted) and then used, sealed, for the Ingests they trigger.
- An Ingest records Broadcasts as such (real start and end times), fetches Replies along with top-level comments, stores each comment's `authorChannelId`, and, when asked, captures the live chat of any Broadcast that is on air during the run.
- A new `/search` page lets anyone search the Catalog by terms, date range, author and record kind, with sorting and pagination. Each SearchHit links to the video page in the app and to YouTube, at the right second when one is known.
- The video page shows a Broadcast's LiveChatMessages next to its TimestampedComments.

## User Stories

### OperatorKey

1. As an Operator, I want to paste my YouTube Data API key into the web app, so that Ingests spend my own project's quota.
2. As an Operator, I want the key checked when I submit it, so that I learn about a typo before an Ingest fails on the runner.
3. As an Operator, I want a distinct message for an invalid key, so that I know to copy it again.
4. As an Operator, I want a distinct message when the key's quota is exhausted, including when it resets (midnight Pacific), so that I know when to retry.
5. As an Operator, I want a distinct message when the YouTube Data API is not enabled on the key's project, so that I know which console switch to flip.
6. As an Operator, I want a distinct message when the key is restricted (HTTP referrer or IP restrictions), so that I can loosen the restriction for this use.
7. As an Operator, I want the key remembered in my browser, so that I do not paste it for every Ingest.
8. As an Operator, I want to forget the stored key with one action, so that I can rotate it or leave a shared computer clean.
9. As an Operator, I want Ingests to fall back to the repository's key when I have not supplied one, so that v1 behavior keeps working.
10. As an Operator, I want my key never to appear in the database, in logs, or in the dispatch payload, so that a public repository does not leak it.
11. As a Visitor, I want key checks to need the operator token, so that nobody can use the site to test stolen keys.

### Catalog creation

12. As an Operator, I want to create a Channel's Catalog from an `@handle`, a `UC…` id or a URL, as in v1, so that I can start from whatever I have at hand.
13. As an Operator, I want Broadcasts that have ended recorded as Broadcasts, so that I can tell streams from uploads.
14. As an Operator, I want each Broadcast's real start and end time recorded, so that chat offsets and durations are correct.
15. As an Operator, I want a Broadcast that is on air during an Ingest recorded as on air, so that the next Ingest can mark it as ended.
16. As an Operator, I want scheduled Broadcasts that have not started yet skipped, so that the Catalog holds only content that exists.
17. As an Operator, I want Replies ingested together with top-level comments, so that an author's activity is complete.
18. As an Operator, I want each comment's `authorChannelId` stored, so that an author stays identifiable when they rename themselves.
19. As an Operator, I want to opt in to live-chat capture per IngestRequest, so that I spend chat quota only when a Broadcast is on air.
20. As an Operator, I want live-chat capture to stop at a quota budget, so that one long Broadcast cannot burn the whole day.
21. As an Operator, I want captured chat kept even if the run is cut off, so that a long Broadcast is not all-or-nothing.
22. As an Operator, I want the status area to show videos, comments, Replies and LiveChatMessages written, plus quota used, so that I can see progress.
23. As an Operator, I want the status area to show how many videos were skipped because comments are disabled, so that missing comments are explained.
24. As an Operator, I want a failed Ingest to say why (invalid key, quota exhausted, Channel not found, dispatch failed), so that I can act on it.

### Search

25. As a Visitor, I want to search comment text by one or more terms, so that I can find who said something.
26. As a Visitor, I want every term to have to match, so that adding a term narrows the results.
27. As a Visitor, I want matches to ignore case and accents, so that "acao" finds "Ação".
28. As a Visitor, I want to include video titles and descriptions in the search, so that I can find the video itself.
29. As a Visitor, I want to search LiveChatMessages too, so that reactions during a Broadcast are findable.
30. As a Visitor, I want to filter by the comment's date range, so that I can see what was said in a given period.
31. As a Visitor, I want to filter by the video's publication date range, so that I can limit the search to a season of videos.
32. As a Visitor, I want to filter by author display name, so that I can see what one person wrote.
33. As a Visitor, I want to filter by an author's channel id, so that a renamed author is still found.
34. As a Visitor, I want to filter by record kind (comment, Reply, LiveChatMessage, video), so that I can focus the results.
35. As a Visitor, I want to scope the search to one Channel, so that results do not mix creators.
36. As a Visitor, I want to restrict the search to TimestampedComments, so that every result jumps to a moment.
37. As a Visitor, I want to sort by newest, oldest or most liked, so that I can pick the ordering that fits the question.
38. As a Visitor, I want results paginated, so that large result sets stay fast.
39. As a Visitor, I want the search to be a plain URL (GET form), so that I can bookmark and share it.
40. As a Visitor, I want the page to work without JavaScript, so that it loads anywhere.
41. As a Visitor, I want a clear empty state when nothing matches, so that I know the search ran.
42. As a Visitor, I want expired comment text never to appear in results or to match a search, so that the Catalog stays within YouTube's 30-day rule.

### SearchHit links

43. As a Visitor, I want each SearchHit to link to the video page in the app, so that I can read the surrounding conversation.
44. As a Visitor, I want each SearchHit to link to the video on YouTube, so that I can watch it.
45. As a Visitor, I want a comment with TimeAnchors to link to YouTube at the first anchor's second, so that I land on the moment it cites.
46. As a Visitor, I want every TimeAnchor of a hit listed as its own link, so that I can choose the moment.
47. As a Visitor, I want a LiveChatMessage hit to link to YouTube at its offset, so that I see what was on screen when it was written.
48. As a Visitor, I want a SearchHit to show its title, author, date and kind, so that I can judge it without opening it.
49. As a Visitor, I want the matched terms highlighted in the snippet, so that I can see why it matched.
50. As a Visitor, I want a Reply hit to show which comment it answers, so that it makes sense on its own.

### Video page

51. As a Visitor, I want a Broadcast's page to show it is a Broadcast, with its real start time and duration, so that I know what I am looking at.
52. As a Visitor, I want a Broadcast's page to list its LiveChatMessages by offset, each linking to that second, so that I can replay the chat against the video.
53. As a Visitor, I want Replies shown under their top-level comment, so that conversations read naturally.
54. As a Visitor, I want a finished Broadcast without captured chat to say "chat not captured", so that the absence is explained rather than looking like a bug.

### Operations

55. As an Operator, I want the local CLI to keep working with `.env`, so that dev, tests and repair stay offline-capable.
56. As an Operator, I want `pnpm ingest --live-chat` locally, so that I can capture a Broadcast from my workstation.
57. As an Operator, I want search to behave the same on local SQLite and on D1, so that what I test is what ships.

## Implementation Decisions

### Modules

- **Ingest pipeline (deepened).** The pipeline becomes a sequence of composable stages (resolve Channel → list videos → enrich and classify → comments and Replies → live chat) behind one interface: an Ingest takes a context (client, quota-billing `call`, clock, logger, a row sink) and streams rows to the sink stage by stage, instead of returning one in-memory bundle. The local sink still commits one atomic batch. The remote sink flushes in chunks (ADR-0003), which live chat needs. The first refactor ticket changes no behavior.
- **Catalog read model vs Ingest write model.** The current queries module is split. Ingest writes (upserts, statement builders) stay with the pipeline's sink. Catalog reads (catalog list, video by id, comments of a video, anchors, LiveChatMessages, search) form their own module. Search is built by a small portable filter builder that turns a SearchQuery into one parameterized SQL string. No string interpolation of values, positional `?` only.
- **Text normalizer** (in `db`). It turns text into `search_text`: Unicode NFKD, combining marks removed, lowercase, every run of non-letter/digit characters collapsed into one space, trimmed. Ingest uses it on write, search uses it on query terms.
- **YouTube client** gains `liveStreamingDetails` on `videos.list`, `part=snippet,replies` on `commentThreads.list`, `comments.list` by `parentId` (paged), and `liveChatMessages.list` (paged, returns `pollingIntervalMillis`, `offlineAt`, `nextPageToken`). Quota stays the caller's job through the existing `QuotaCounter`. Costs: `liveChatMessages.list` 5 units, everything else 1.
- **Live-chat capture.** A loop: poll, emit LiveChatMessages, wait `pollingIntervalMillis` (via an injected sleep), repeat until the chat ends, the chat budget runs out, or the wall-clock cap (5 h) is reached. Its clock and sleep are seams.
- **OperatorKey check route** (`server/api`). Token-gated `POST /api/key/check` with `{ key }` returns `{ ok: true }` or `{ ok: false, reason, message }`. It calls `fetch` directly with an injectable transport (ADR-0007).
- **Key sealing.** `server/api` seals with RSA-OAEP-256 under `INGEST_SEAL_PUBLIC_KEY`, and `cli` unseals with `INGEST_SEAL_PRIVATE_KEY`. Format `v1.<base64url>` (ADR-0008).
- **SSR.** A new `GET /search` route and template. Video-page additions: a Broadcast badge, LiveChatMessages, Reply nesting. The operator panel gets the key field, the check button and the live-chat checkbox.

### Classification of Broadcasts

- `liveStreamingDetails` absent → `kind = 'upload'`.
- `liveStreamingDetails` present → `kind = 'broadcast'`, with `broadcast_state` from `snippet.liveBroadcastContent` and `actualEndTime`: `live` (on air), `ended` (`actualEndTime` set), `upcoming` (not started; **skipped**, not stored).
- The API does not distinguish a premiere from a live stream. Both are Broadcasts, and no heuristic is attempted (GLOSSARY).

### Replies

- Fetch `commentThreads.list?part=snippet,replies`. When `snippet.totalReplyCount` is greater than the number of embedded `replies.comments`, page `comments.list?parentId=…` (1 unit/page). Otherwise use the embedded subset, at no extra cost.
- A Reply is a CommentRecord with `parentId` set. It gets TimeAnchor detection, `authorChannelId`, TTL and search exactly like a top-level CommentRecord.
- Quota: Replies add at most one call per thread that has more Replies than YouTube embeds. The existing 8,000-unit warning and 9,500-unit abort apply to the whole run.

### LiveChatMessage

- Fields: `id`, `videoId`, `channelId`, `author`, `authorChannelId`, `text`, `publishedAt`, `offsetSeconds = max(0, floor((publishedAt − actualStartTime) / 1000))`, `fetchedAt`.
- Only `textMessageEvent` and the `userComment` of `superChatEvent` are stored (ADR-0009).
- TimeAnchors are not detected in LiveChatMessages: the offset already says when.

### Schema: migration `0003_v2_catalog.sql` (new file; 0001/0002 untouched)

- `videos` + `kind TEXT NOT NULL DEFAULT 'upload' CHECK (kind IN ('upload','broadcast'))`, `broadcast_state TEXT CHECK (broadcast_state IN ('live','ended'))`, `actual_start_time TEXT`, `actual_end_time TEXT`, `search_text TEXT NOT NULL DEFAULT ''`.
- `comments` + `author_channel_id TEXT NOT NULL DEFAULT ''`, `parent_id TEXT REFERENCES comments(id) ON DELETE CASCADE`, `search_text TEXT NOT NULL DEFAULT ''`. Indexes `(channel_id, published_at)`, `(author_channel_id)`, `(parent_id)`.
- New `live_chat_messages` table with the fields above, FKs to `videos` and `channels`, and indexes `(video_id, offset_seconds)`, `(channel_id, published_at)`, `(author_channel_id)`.
- `ingest_requests` + `key_source TEXT NOT NULL DEFAULT 'repo' CHECK (key_source IN ('repo','operator'))`, `capture_live_chat INTEGER NOT NULL DEFAULT 0`, `replies_written`, `chat_messages_written`, `skipped_videos`, `quota_used` (INTEGER NOT NULL DEFAULT 0).
- `comments_active` is dropped and recreated in the new migration so that it exposes the new columns and redacts `search_text` to `''` when expired. A matching `live_chat_messages_active` view is added. The view's existing column names keep their meaning.
- Backfill: `UPDATE comments SET search_text = lower(text)` and the same for videos (ASCII-only best effort; the next Ingest rewrites them).

### SearchQuery contract (`GET /search`)

| Param            | Meaning                                                                                       |
| ---------------- | --------------------------------------------------------------------------------------------- |
| `q`              | Terms, whitespace-separated, all must match (normalized). Max 8 terms, each ≥ 2 chars.         |
| `kind`           | Repeatable: `comment`, `reply`, `chat`, `video`. Default: `comment`, `reply`, `chat`.         |
| `channel`        | `UC…` id; default all Channels.                                                               |
| `from`, `to`     | `YYYY-MM-DD`, inclusive, on the hit's own `publishedAt` (UTC).                                |
| `videoFrom/To`   | `YYYY-MM-DD`, inclusive, on the source video's `publishedAt`.                                 |
| `author`         | `UC…` (24 chars) → exact `authorChannelId`; otherwise normalized substring of display name.   |
| `timestamped`    | `1` → only CommentRecords with TimeAnchors (and all LiveChatMessages, which have an offset).  |
| `sort`           | `newest` (default), `oldest`, `likes` (LiveChatMessages and videos sort as 0 likes).          |
| `page`           | 1-based; 25 hits per page; max page 40.                                                       |

- Invalid parameters render the form with an inline message (HTTP 400), never a 500.
- A query with no `q`, no author and no date range shows the empty form, not the whole Catalog.
- Expired CommentRecords and LiveChatMessages never match and are never shown (ADR-0001/0010).

### SearchHit links

- App: `/v/{videoId}`, plus `#c-{commentId}` or `#m-{messageId}`.
- YouTube, comment or Reply with TimeAnchors: `https://www.youtube.com/watch?v={videoId}&t={firstAnchorSeconds}s`, and one link per anchor.
- YouTube, comment without anchors: `https://www.youtube.com/watch?v={videoId}&lc={commentId}` (YouTube highlights the comment).
- YouTube, LiveChatMessage: `https://www.youtube.com/watch?v={videoId}&t={offsetSeconds}s`.
- All external links keep `target="_blank" rel="noopener noreferrer"` (v1 §6).

### OperatorKey check contract

- `POST /api/key/check`, `Authorization: Bearer <operator token>`, body `{ "key": "AIza…" }`.
- Local shape check first (`^AIza[A-Za-z0-9_-]{30,50}$`). Then `channels.list?part=id&id=<fixed public channel>&key=…`.
- Mapping: 200 → `ok`. 400 `keyInvalid` or `API_KEY_INVALID` → `invalid`. 403 `quotaExceeded` → `quotaExceeded`. 403 `accessNotConfigured` → `apiNotEnabled`. 403 `ipRefererBlocked` or `forbidden` → `restricted`. Network error or 5xx → `unavailable`.
- `POST /api/ingest` accepts `{ channel, key?, captureLiveChat? }`. When `key` is present it is checked, then sealed and dispatched. A failed check returns `422 { reason, message }` without creating an IngestRequest.

### Secrets inventory delta

- Worker var `INGEST_SEAL_PUBLIC_KEY` (public JWK). Repo secret `INGEST_SEAL_PRIVATE_KEY`. The workflow receives `client_payload.sealedKey` and `client_payload.captureLiveChat` through env, and masks the unsealed key before use.

## Testing Decisions

- Tests exercise external behavior through the highest existing seam and never mock modules (AGENTS.md). Every test runs without the network.
- **Ingest:** through `runIngest` with the fake `transport`, `now`, `quota` and `writer`, plus a `sleep` seam for chat polling. Fixtures: one Channel with 1 upload, 1 ended Broadcast, 1 on-air Broadcast with 2 chat pages and `offlineAt` on the last page, threads with embedded and paged Replies, and one video with `commentsDisabled`. Assertions are on the rows written and the quota billed. Prior art: `src/cli/ingest.test.ts`, `src/ingest/pipeline.test.ts`.
- **Search:** through `createApp(...).request('/search?...')` over a seeded in-memory SQLite `Executor`, asserting the hits rendered. A clock-shifted fixture proves expired rows neither match nor render. The same queries also run through the D1 executor test double (`src/db/d1.test.ts` prior art) to keep the SQL portable. Prior art: `src/server/routes.test.ts`, `src/server/ssr.test.ts`.
- **Normalizer:** pure unit tests (accents, case, punctuation, emoji).
- **Key check and sealing:** through `createApp` with an injected transport, covering each Google error envelope. A seal/unseal round-trip test imports both sides, which test files are allowed to do.
- **Architecture:** `src/architecture.test.ts` stays as it is and must stay green. No v2 change needs a boundary edit.
- **End to end (Phase D):** a fixture Ingest of a fake Channel (1 upload + 1 Broadcast with chat) into SQLite, then search by term, date and author, then follow the hit's `&t=` link. Also a manual check of `/search` on `pnpm dev` and `pnpm dev:worker`.

## Out of Scope

- Several Operators, accounts, per-person Catalogs, and the 7-day deletion affordance that would come with them.
- Google sign-in / OAuth (ADR-0007).
- Chat replay of Broadcasts that have already ended, and any unofficial endpoint (ADR-0009).
- Chat events other than text and Super Chat text. Polls, memberships and moderation events.
- FTS5, relevance ranking, stemming and phrase search (ADR-0010). Terms are ANDed substrings.
- Ingest inside the Worker. Scheduled or periodic Ingest.
- In-page YouTube embed and seek (v1 out-of-scope stands).

## Further Notes

- **Quota risk.** Chat polling costs about 5 units per poll. A 2 h Broadcast at a 5 s interval would cost about 7,200 units, which is why the default chat budget is 3,000. Replies add calls only for threads with more Replies than YouTube embeds.
- **D1 risk.** Write rows grow with Replies and chat (ADR-0005's 100k rows/day). Search reads scale with Channel size (ADR-0010).
- **ToS.** Only official endpoints are used. The 30-day rule now covers LiveChatMessages too.
- **Unverified from primary sources** (the Google and Cloudflare docs hosts were blocked by the network policy during design and implementation; every item below is built and tested against fixtures only):
  - the 5-unit cost of `liveChatMessages.list` (`QUOTA_COST.listLiveChatMessages`);
  - its REST path, `GET youtube/v3/liveChat/messages`;
  - the reasons that mean "chat over": `liveChatEnded`, `liveChatNotFound`, `liveChatDisabled` (on 403 or 404);
  - the Google error reason strings the OperatorKey check maps (`keyInvalid`, `API_KEY_INVALID`, `INVALID_ARGUMENT`; `quotaExceeded`, `dailyLimitExceeded`, `rateLimitExceeded`; `accessNotConfigured`, `SERVICE_DISABLED`; `ipRefererBlocked`, `forbidden`, `API_KEY_*_BLOCKED`);
  - that `&lc={commentId}` makes YouTube highlight the comment;
  - `json_each` in author search on real D1: it runs on local SQLite and the D1 test double, not yet against a production D1.

## Implementation notes

Recorded after Phase F (D1, #55). They refine the text above; no ADR changes.

- **Ingest tallies.** `comments=` in the summary line and `ingest_requests.comments_written` count top-level CommentRecords only; Replies are counted apart in `replies=` / `replies_written`. `skipped=` / `skipped_videos` counts upcoming Broadcasts (not stored) plus videos whose comments were skipped for `commentsDisabled` or `videoNotFound`. `chat=` / `chat_messages_written` counts LiveChatMessages written.
- **Stages.** The Ingest runs as stages (`src/ingest/stages.ts`) into a row sink. The main run buffers into one write (one atomic batch locally); the live-chat stage (`src/ingest/live-chat.ts`) runs after that write and flushes each poll, so a run cut short keeps what it captured.
- **Author search.** Display names cannot be folded in SQL (SQLite and D1 have no accent folding). One extra query reads the distinct author names in scope, `normalizeSearchText` folds them in JS, and the matching raw names go back into the search as one JSON-array param (`author IN (SELECT value FROM json_each(?))`). This keeps offset pagination exact and stays under D1's bound-parameter cap. ADR-0010 still holds: terms are still `LIKE` over `search_text`, no FTS5.
- **Timestamped filter on the video page.** The "Timestamped" chip shows timestamped CommentRecords and Replies. A top-level CommentRecord with no TimeAnchor of its own but a timestamped Reply stays visible as that Reply's context; its other Replies are hidden.
- **End to end.** `src/e2e.test.ts` runs one fixture Ingest with `--live-chat` into SQLite, then `/search` by term, date range, author and kind, and follows the app links into `/v/:videoId`.
